# Работа с IZO ASA Platform

Прочитать README, затем docs/STATUS.md и карту нужного модуля в docs/ARCHITECTURE.md.
Не читать старый IZO_ASA и исторические планы без конкретной необходимости.

1. Одна задача — одна ограниченная ветка и PR. До правки проверить remote, HEAD,
   status и чужие изменения. Не использовать reset --hard, force-push и cleanup.
2. Описать пользовательский результат, область изменений, проверки и ограничения
   в PR. Отдельный многостраничный Task Contract для кнопки не нужен.
3. Чистые contracts/generation не импортируют HTTP, БД, SDK и секреты.
   UI не вызывает провайдеров и не содержит ключи. Общий HTTP-клиент один.
4. Один responsive web app. Telegram/MAX — адаптеры, не копии приложения.
   Непроверенные initData, query parameters и JS globals не дают identity.
5. Генерации API и local получают разные pools. GPU-worker в будущем имеет
   исходящее HTTPS-соединение, не доступ к PostgreSQL и не роль CI-runner.
6. Unit/UI тесты не используют сеть, production, платных провайдеров или GPU.
   Compose-интеграция идёт только с временными DB/S3. Секреты не печатать.
7. Любые реальные платежи, письма, bot actions, деплой, DNS и ключи требуют
   отдельного разрешения владельца; текущая задача этого не разрешает.
8. После маленькой правки — профильная проверка. Не чинить production ради
   кнопки. Общий CI — при готовом PR, не после каждой строки.
9. Не менять LICENSE, CI, миграции и правила контроля вместе с посторонней
   продуктовой задачей. CODEOWNERS не заменяет настройки branch protection.
10. Не повышать лимиты файлов ради зелёного теста. Выделять связную функциональность,
    а не произвольные куски. Нужен и лимит строк, и разумный объём файла.
11. Не обещать exactly-once для внешнего провайдера. Неясный результат требует
    reconciliation, а не автоматической повторной платной генерации.
12. Разделять IMPLEMENTED / TESTED / PUSHED / MERGED / DEPLOYED. Эмуляция Mini App
    не доказывает работу в настоящем приложении. CI success проверять по шагам.
