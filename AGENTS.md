# IZO ASA · правила разработки

Один продукт: Account / Credits / Jobs / Media общие для всех провайдеров и клиентов. Правила ниже обязательны; ближайший `AGENTS.md` уточняет область, но не отменяет безопасность. Команды запуска — README, карта — docs/INDEX.md.

## Начать с малого

Прочитать этот файл, краткий STATUS, карточку одного пакета NEXT и только нужные U/D/A/AD/S-карточки PRODUCT/ADMIN/UX/AI_RUNTIME. Затем открыть конкретный source/test, не весь репозиторий. Сначала поиск имён/путей, потом диапазоны строк. Не читать lockfiles/generated/binary/history/старый IZO_ASA без доказанной необходимости. Не прикладывать весь каталог страниц к задаче кнопки.

До правки: repository, base SHA/ветка, git status, чужой WIP, ожидаемое поведение, сохраняемые инварианты, допустимые файлы и проверки. Одна задача — одна ветка/PR; один пишущий агент на пересекающуюся область. Не reset --hard, force push, cleanup чужих данных или автоматический merge/deploy.

## Неизменяемые границы

- Один responsive UI, platform adapters Telegram/MAX не отдельные приложения. JS hints/initDataUnsafe/client user_id не дают identity. QHD/4K/HiDPI и реальные OS scaling различаются; эмуляция не доказывает настоящий Mini App.
- Routes/UI не содержат provider keys, отдельный ledger или прямой provider fetch. Контракты и чистые правила не импортируют инфраструктуру. Новый adapter/connection/credential source — по AI_RUNTIME §9–10, без второго ядра.
- Роль, состояние аккаунта, план и остаток независимы. Scope/ownership проверяются сервером. Private files не становятся общими из-за URL. Пустой /admin не является защитой.
- API/local pools разделены. GPU-worker — outbound HTTPS, без БД/shell/custom arbitrary workflow и без роли GitHub runner. Unknown outcome сначала reconcile; слепые повторы платных запросов и local→paid без согласия запрещены.
- Секреты/production/платные API/GPU не нужны unit/UI tests. Integration только с изолированными DB/S3. Реальные платежи, письма, боты, ключи, DNS и выпуск требуют отдельного разрешения и бюджета. Product AI не получает GitHub/shell/Docker права coding-агента.

## Экономный цикл правки

Сначала воспроизвести ошибку или определить acceptance case. После правки запустить ближайший тест; не повторять Full suite после каждой строки. Общий CI перед приёмкой сохраняется. Не устанавливать уже установленные зависимости без изменения lock/runtime. Не обновлять библиотеки ради UI-задачи.

После двух одинаковых неудач остановить повтор, записать конкретную причину и изменить гипотезу. Расширять чтение только к найденной зависимости. Не переписывать всё приложение и не ослаблять tests/snapshots/limits ради зелёного результата. Отдельно назвать расширение scope до изменения общего контракта, CI, миграций, LICENSE или правил.

Перед публикацией: `python tools/check_change.py --base <согласованный SHA> --scope <файл scope>` в полном git checkout. Команда только проверяет пути/размер изменения и печатает рекомендуемые проверки; не исполняет их и не заменяет CI/review. Если нет инструмента/полного checkout, честно указать это и сверить remote compare. Нельзя объявлять проверку выполненной по наличию её файла.

Для малой UI-задачи ориентир первого чтения — до 6 релевантных файлов; это диагностический бюджет, не запрет обоснованного расширения. Machine scope для пакета содержит конечный лимит файлов. Превышение требует разделения задачи или явного пересмотра, не автоматического повышения лимита. Количество файлов не заменяет проверку ответственности.

## Передать результат

В PR: задача/ID, base и head, изменённое поведение, затронутые области, команды/результаты, ограничения, следующий один шаг. Только краткое резюме ошибки, не гигантские сырые логи. Фактические tokens/стоимость при доступности; иначе «нет данных», не оценка экономии как факт.

IMPLEMENTED / TESTED / REVIEWED / PUSHED / MERGED / DEPLOYED независимы. Самопроверка не независимое review; CI проверяется по SHA/steps. CODEOWNERS/AGENTS/check_change не защищают main от владельца широкого token: branch protection и review настраиваются отдельно. Нынешний дизайн требует решения владельца.

Не дублировать план: NEXT — порядок, STATUS — факты, предметная страница — поведение. Новая U/D/A/AD/S сначала получает карточку в её владельце. При handoff передать branch/SHA, scope, проверки и нерешённое без ключей и всей истории чата.
