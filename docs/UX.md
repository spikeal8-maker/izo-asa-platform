# Интерфейс и взаимодействие · IZO ASA 0.1

Статус: требования к будущему UX/UI. Техническая оболочка Foundation **не принята как дизайн**. Новое оформление не обязано копировать старый сайт; сохраняется понятность продукта и одна система взаимодействия.

## 1. Что означает «качественно»

Пользователь понимает, где находится, что вводить, сколько стоит запуск и где появится результат. На телефоне доступны те же существенные действия, но не сжатая desktop-страница. Ошибки исправимы, исходники/черновики не теряются, активная генерация не исчезает при навигации.

Внешний вид оценивает владелец по интерактивному прототипу. Автотесты подтверждают поведение/часть доступности, не художественное качество. Скриншот сам по себе не доказывает работу загрузки, оплаты или реального Mini App.

## 2. Информационная архитектура — предложение для UX-001

Гость: краткая страница продукта, примеры с разрешёнными правами, ссылка на ленту, понятный вход. Зарегистрированный пользователь: рабочее пространство, переключение направлений, мои работы, лента, аккаунт. Админка открывается только сотруднику и визуально отделена от создания контента.

Общие слова: «Мои работы» — приватная галерея; «Лента» — публичные публикации; «Баллы» — единицы продукта; «Задания» — выполняющиеся/завершённые операции. Не использовать два разных названия одной сущности на телефоне и desktop.

Точные маршруты и первая страница после входа ещё не утверждены. Chat-first допустимая концепция, но не повод спрятать прямые рабочие инструменты. UX-001 сравнивает вход в рабочее пространство и путь к image flow; после выбора фиксируется одна route map, которая используется компонентами и тестами.

Не показывать девять равнозначных пунктов в маленькой нижней панели. Предлагаемый mobile-layout: главные действия в короткой нижней навигации, направления внутри рабочего пространства, редкие настройки в отдельной панели. Desktop использует ширину для результата и параметров; tablet перестраивает колонки, не копирует телефон механически.

## 3. Ближайший дизайн-пакет UX-001

Подготовить одну проработанную визуальную концепцию, а не галерею из десятка несвязанных макетов. Артефакт — интерактивный прототип с fake data, явно не production.

Обязательные экраны: студия изображения до запуска; эта же студия с выполняющейся задачей/результатом/ошибкой; приватная галерея и подробный просмотр работы. Показать вход/меню и короткий пример административной таблицы, чтобы проверить общие компоненты, не рисовать сразу всю админку.

Обязательные варианты: телефон, планшет, desktop, включая QHD/«2K» и 4K UHD по матрице раздела 6; узкий/широкий viewport и переполнение длинного русского текста. Проверить light/dark как систему, при этом точная палитра и стартовая тема входят в утверждение, а не переносятся случайно из Foundation.

Владелец принимает: расположение действий, читаемость, путь до результата, карточки, поведение на телефоне и общее направление оформления. Только после этого развиваются остальные экраны. До согласования нельзя превратить первый неудачный shell в сотни зависимых CSS-правил.

## 4. Единые компоненты

Design tokens: цвет/контраст, typography, spacing, radius, elevation, focus, motion, breakpoints. Один источник tokens, не новые оттенки на каждой странице. Стили ограничены компонентом/feature; глобальный stylesheet содержит reset и tokens, не все страницы.

Библиотека: Button, IconButton, Input/Textarea, Select/Combobox, FileDropzone, Tabs, Dialog/Sheet, Toast, Price/Balance, JobCard, AssetCard, EmptyState, ErrorState, Pagination. Компоненты имеют loading/disabled/error/focus состояния. Повторный клик по занятому submit не создаёт новую операцию.

В модальном окне: понятный заголовок, focus trap, Escape где допустимо, возврат focus, предупреждение о несохранённых данных. Bottom sheet — способ представить тот же сценарий, не отдельная бизнес-логика.

Контент: настоящие разрешённые assets или честные тестовые примеры; без случайных размытых заглушек, изображающих готовую генерацию. Не копировать дизайн/изображения конкурентов как собственные. Не включать proprietary font files в открытый репозиторий без соответствующих прав.

## 5. Обязательная матрица состояний

| Область | Состояния, которые нужно нарисовать и проверить |
|---|---|
| Вход | Пусто, заполнение, ошибка, занято, доставка/подтверждение, истёкший код, восстановление |
| Выбор модели | Загрузка, доступные, отключённая, нет подходящей, недостаточный доступ |
| Загрузка исходника | Выбор, прогресс, проверка, слишком большой/неверный, повтор, удаление |
| Студия | Черновик, расчёт цены, недоступный provider, недостаток баллов, submit, задача выполняется |
| Результат | Готов, подготовка preview, нет preview, ошибка скачивания, переход к следующему действию |
| Галерея/лента | Пусто, loading, данные, offline/ошибка, конец страницы, moderation/удалено |
| Чат | Пустой диалог, streaming, tool confirmation, tool running/result/error, оборванная сеть |
| Admin | Загрузка, нет permission, нет результатов, подтверждение, conflict, audit receipt |

Пустая галерея предлагает создать работу, а не демонстрирует чужие тестовые изображения как принадлежащие пользователю. Недоступный provider объясняется человеческим текстом, не внутренним stack trace. Длинное ожидание показывает возможность уйти и вернуться, а не заставляет держать страницу открытой.

## 6. Телефон, планшет, desktop, QHD и 4K

Требование владельца: качественная адаптация включает большие экраны 2K/4K, а не заканчивается на Full HD. Для проверяемой спецификации «2K» здесь обозначает QHD 2560×1440; 4K UHD — 3840×2160. Термин не заменяет точные размеры теста. Это разрешение отображения интерфейса, не обязательное разрешение каждой AI-генерации.

Базовые CSS viewport-проверки: 360×800, 390×844, 768×1024, 1024×768, 1440×900, 1920×1080, **2560×1440**, **3840×2160**. Дополнительно проверяется HiDPI: **1920×1080 CSS px с deviceScaleFactor=2** и **2560×1440 CSS px с deviceScaleFactor=1.5**. Размер screenshot в device pixels зависит от DPR и режима снимка; нельзя смешивать его с CSS viewport в отчёте.

Это целевая расширенная матрица UX-001, ещё не добавленная в Playwright config текущим документационным пакетом. Старые 30 shell-тестов не доказывают QHD/4K/HiDPI. В PR реализации указать viewport, DPR, browser, режим zoom и реальные выполненные сценарии.

### 6.1. Масштабирование и поведение широкого экрана

Breakpoint выбирается по доступному CSS-пространству/контейнеру, не только по физическому разрешению монитора. ОС scaling, browser zoom и DPR — связанные, но не одинаковые настройки. Эмуляция DPR не доказывает правильную работу настоящего Windows scaling; отдельно проверяются 125/150/200% и browser zoom на реальном стенде с записанными параметрами. На 4K при 200% может быть около 1920 CSS px по ширине, а не 3840; высоту дополнительно занимает интерфейс браузера.

На большом экране студия использует место для preview/canvas и доступных панелей, галерея — для разумной сетки карточек, админка — для таблиц/деталей. Не растягивать абзац чата на всю ширину 4K и не оставлять всё рабочее пространство узкой телефонной колонкой. Ширина текстового чтения ограничена; ширина canvas и сеток регулируется отдельно. Точные размеры колонок утверждаются в UX-001.

Размеры шрифта и управления задаются читабельными tokens с ограничениями, а не одним vw для всего интерфейса. Нельзя исправлять 4K общим CSS transform:scale, уменьшением всего сайта или запретом пользовательского zoom. На 100% и увеличенном масштабе основные действия доступны, текст не обрезается, модальные окна остаются в viewport.

### 6.2. Чёткость и ресурсы

UI-иконки/геометрические элементы — векторные где применимо; растровые previews имеют подходящие размеры/srcset/sizes. Маленькая thumbnail не растягивается как качественный full-screen original. Высокое разрешение монитора не должно автоматически скачивать оригиналы всех работ; выбор ресурса зависит от реально отображаемого размера, DPR и бюджета трафика/памяти.

Canvas/3D-viewer согласуют CSS-размер и drawing buffer с DPR, но ограничивают ресурсы по принятому бюджету; проверяются резкость, pointer coordinates и отсутствие огромных необоснованных буферов. Нельзя считать screenshot 4K доказательством чёткости реального видео/3D или качества исходного файла.

### 6.3. Общие ограничения устройств

Нет горизонтальной прокрутки всей страницы; исключение — явно ограниченный canvas/таблица с доступными альтернативами. Экранная клавиатура не закрывает активное поле/submit. Safe areas и изменение высоты viewport учитываются. Основные действия не требуют hover, drag имеет альтернативу там, где это возможно.

Большие previews загружаются лениво; видео не запускает звук автоматически; 3D/viewer открывается по потребности. Полный файл не загружается на карточку галереи. Touch, мышь и клавиатура поддерживают общий сценарий. Черновик не хранит пароль, токен и большие base64-медиа в localStorage.

## 7. Telegram/MAX — общий UI, отдельные адаптеры

Адаптер отвечает за back, theme, viewport/safe areas, открытие ссылок, share/download и presentation readiness. Отсутствующая возможность имеет browser fallback или ясное сообщение. Подключение SDK не должно ломать обычный браузер.

Identity подтверждается только backend. JS platform hint используется для оформления, не для прав. Mini Apps проверяются на реальных поддерживаемых клиентах, включая клавиатуру, загрузку из фото/файлов, возврат после сворачивания, скачивание/передачу результата и восстановление сессии.

Не требовать всем браузерам одинаковый third-party-cookie режим: точная схема session/cookie проверяется на выбранных WebView и HTTPS-origin в этапе PLATFORM. Обход проверки подписи ради работающего демо запрещён.

## 8. Доступность и измеримые цели

Цель продукта — WCAG 2.2 AA для обычных UI-поверхностей; заявление о соответствии возможно только после проверки. Наш дизайн-ориентир для основных touch-кнопок — минимум 44×44 CSS px, а не ошибочное утверждение, что AA всегда требует именно 44 px. WCAG 2.2 AA Target Size Minimum имеет собственные условия/исключения и базовый размер 24×24.

Клавиатурная навигация, видимый focus, доступные имена элементов, корректные labels/errors, достаточный контраст, reduced motion и отсутствие сообщения только цветом обязательны. Live-объявления прогресса не должны зачитывать каждое процентное изменение.

Предлагаемые бюджеты для проверки на фиксированном профиле: LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 на 75-м процентиле реальных посещений после запуска. Пока трафика нет — лабораторный baseline с указанными устройством/сетью, не выдуманные production-метрики. Не переносить эти пороги на время AI-генерации.

## 9. Критерии приёмки каждого UI-пакета

Проверены заявленные сценарии и состояния; нет ошибок в console; клавиатурный focus корректен; нет page overflow; пользователь понимает цену/приватность; на телефоне действия достижимы; приложены снимки и описание реального поведения. Изменение общих компонентов проверяется на зависимых страницах, а не только на красивом главном экране.

Скриншотные эталоны обновляются с объяснением, а не чтобы скрыть regression. Реальный API smoke не заменяется fake-тестом. Изменение текста цены без изменения расчёта не требует переписывания credits; изменение значения цены — уже cross-domain задача с отдельными проверками.
