# Разработка с coding-агентами · IZO ASA

Цель: небольшое изменение должно требовать небольшого контекста и проверяемого результата. Этот документ описывает работу разработчика; поведение пользовательского AI — в [AI_RUNTIME](AI_RUNTIME.md). Обязательные краткие ограничения — [AGENTS](../AGENTS.md).

## 1. Кто за что отвечает

Владелец формулирует желаемый пользовательский результат, принимает дизайн/бизнес-решения и разрешает реальные затраты/выпуск. Архитектурный ведущий превращает запрос в ограниченный пакет, выбирает нужные контракты и объясняет компромиссы. Coding-агент реализует пакет и проверки. Reviewer отдельно проверяет diff и доказательства. Release-оператор устанавливает разрешённый артефакт.

Это роли процесса, не требование нанять пять человек или запускать пять ботов. На старте один агент пишет код, второй проход выполняет review без добавления функций. Самопроверку нельзя называть независимым review. Владельцу не требуется вручную читать весь исходный код.

## 2. Какой контекст нужен агенту

Обязательный минимум: AGENTS → STATUS → нужная карточка NEXT → одна предметная спецификация. Затем конкретный source/test. README открывается для реальных команд, INDEX — когда неясно, где владелец темы. Весь комплект документов не прикладывается к каждой задаче.

| Задача | Сначала читать |
|---|---|
| Навигация, кнопка, responsive, визуал | UX + соответствующий компонент/test |
| Вход, session, права | PRODUCT P-01 + Accounts/security из ARCHITECTURE |
| Компенсация, баллы | ADMIN §5 + Credits из ARCHITECTURE |
| Provider, очередь, worker | AI_RUNTIME + соответствующий contract/adapter |
| Галерея/лента | PRODUCT P-07/P-08 + Media/Feed границы |
| Админская операция | ADMIN + владелец вызываемой команды |
| Docker/release/backup | OPERATIONS; не читать/чинить production для UI |
| Документация/план | INDEX + документ-владелец темы |

Не искать старый приватный IZO_ASA автоматически. Он нужен только как явно запрошенный продуктовый референс. Не загружать lockfiles, generated types, binary assets и весь repository tree без причины. После двух одинаковых неудачных попыток не начинать третий широкий scan: собрать конкретные ошибки и изменить диагностическую гипотезу.

## 3. Карточка задачи — достаточно описания PR/issue

Фиксируются: ID из NEXT, пользовательский результат «до → после», входные требования P-ID, область допустимых файлов/модулей, non-goals, критерии приёмки, профильные тесты, риск и граница отката. Для маленькой кнопки отдельный многостраничный контракт не нужен.

Пример настоящей следующей задачи:

> Выполни UX-001 по docs/NEXT.md и docs/UX.md. Нужен согласуемый интерактивный прототип студии изображения, состояния результата/ошибки и приватной галереи на телефоне, планшете и desktop. Работай только с web UI, fake data и его тестами/документацией. Не менять backend, базу, кредиты, providers, Docker, CI и LICENSE. Нынешний foundation shell не является утверждённым дизайном. Представь одну целостную концепцию, рабочую навигацию и все заявленные состояния. Отдельно укажи, что остаётся макетом. Не объединяй PR и не выполняй deployment. При необходимости общего изменения сначала объясни его влияние и обнови scope.

Это поручение запускается после технического review основания и утверждения scope; текст не означает, что UX-001 уже выполнен.

## 4. Рабочий цикл

1. Проверить remote, branch, HEAD, status, текущие PR и чужие изменения. Не стирать WIP и не force-push.
2. Показать краткий план и область. Уточнять только существенную недостающую информацию, не спрашивать заново уже принятые решения.
3. Для bug — воспроизвести failing case. Для feature — сформулировать acceptance case до реализации. Нельзя выдавать скриншот заглушки за функциональную проверку.
4. Сделать минимальное связное изменение. Не реорганизовывать несвязанные модули «заодно».
5. Запустить профильные tests, проверить diff, ownership/security и необходимые generated contracts.
6. Открыть один понятный PR, дождаться предусмотренных проверок и review в рамках выполняемой работы. Не сообщать результат будущего CI заранее.
7. Обновить STATUS после подтверждённого изменения состояния; описание поведения обновить в его единственном документе. Не копировать длинный лог в каждый файл.
8. Merge и release — отдельные действия с разрешением; для работающего сайта проверить exact version и реальный нужный сценарий.

Результат отчёта: IMPLEMENTED, TESTED (команды/среда/SHA), PUSHED, REVIEWED, MERGED, DEPLOYED, OPERATIONALLY VERIFIED. Каждое поле может быть «нет / не выполнялось». «Работает у меня» не означает Docker/Windows/Mini App verification.

## 5. Проверки по риску

| Изменение | Минимальное доказательство |
|---|---|
| Документ | Существуют ссылки/пути, статус не противоречит коду/PR, diff только в scope |
| Локальная UI-правка | TypeScript/build + целевой UI-сценарий и affected breakpoints |
| Общий компонент | Зависимые screens, keyboard/focus, themes, screenshot review |
| Domain/API | Unit + API contract + integration с временной БД где требуется |
| Auth/credits/jobs/media permissions | Negative access, race/idempotency/restart tests и отдельный review |
| Provider adapter | Fake contract/errors, лимиты, unknown outcome; real test только с разрешением |
| Release | Точный build, схема, backup/restore evidence, health/version и согласованный smoke |

Сегодня существуют команды из README: pytest, export_contracts --check, npm build, Playwright shell и Compose integration. Будущий affected-test router, полный linter/typecheck backend и документационный link checker пока не реализованы; не писать, что они уже защищают проект.

В workflow используется общий CI на PR в main. Не запускать полный suite после каждой строки, но и не урезать gate ради зелёного статуса. Документационный PR не даёт права изменить workflow. Когда CI станет дорогим, маршрутизатор проверок вводится отдельным пакетом с тестами правильности выбора.

## 6. Независимость проверки от production

Unit использует fake dependencies и запрещённую внешнюю сеть. Integration использует временные PostgreSQL/S3. E2E по fake API и E2E по реальному изолированному API маркируются отдельно. Реальные AI-ключи, почта, payments, bot actions и домашний GPU не требуются для обычной разработки.

Нельзя менять код tests так, чтобы пропустить найденный дефект, переобновлять все snapshots без просмотра или считать skipped job успешной проверкой функции. Нельзя выкладывать production transcripts и secrets в public artifacts. Fixture dates и IDs контролируются, не зависят от сегодняшней даты случайно.

## 7. Границы изменений и защита репозитория

CI, LICENSE, permissions, migrations и release scripts — чувствительные области. Их изменение требует отдельного объяснённого scope и reviewer; не проходит вместе с косметической кнопкой. CODEOWNERS/AGENTS сами по себе не блокируют администратора или агента с широким token.

Целевая настройка GitHub: protected main/required checks, PR review, без force pushes, минимальные write-permissions, отдельный защищённый release environment. Если применяемое подключение не позволяет настроить это, состояние честно фиксируется как не выполненное. Это не повод заявлять невозможность ошибки после установки file limits.

Public PR выполняется на GitHub-hosted runner без production secrets. Не исполнять fork-код на GPU-компьютере и не выдавать секреты через pull_request_target. Доступ coding-агента к main/release должен быть уже его доступа к feature-ветке там, где tooling это позволяет.

## 8. Как измерить, что проект стал дешевле менять

После первого image flow выполнить CHANGE-001: три отдельные задачи — изменить мобильную кнопку; изменить правило доступа к модели; изменить обработку provider error. Для каждой записать фактические tokens/стоимость, попытки, длительность тестов и затронутые модули. Если провайдер не даёт token usage, указать «нет данных», не оценивать как факт.

Цель — низкая связность и локализованные изменения; число 1–3 файла не абсолютный закон. Общий компонент может законно потребовать больше зависимых тестов. При изменении реального расчёта цены credits-тесты обязательны; при переносе готового price label не нужен ремонт БД.

Повторный широкий scan, параллельные противоречивые агенты, бесконечные Full suites и изменения вне scope — причины остановить расширение функций и исправить процесс. Бюджет пакета ограничивается до запуска, а не после неожиданного перерасхода.

## 9. Что принимает владелец

Не «тысяча тестов», а показываемый результат: понятный UX, конкретный рабочий сценарий, ясные ограничения, доказательство сохранности/прав. Техническое решение в пределах согласованного scope выбирает разработчик и объясняет обычным языком. Не перекладывать на владельца выбор каждой библиотеки; цену, privacy, внешний вид, публичные обещания и реальные затраты за него молча не решать.
