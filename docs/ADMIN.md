# Администрирование IZO ASA · спецификация 0.1

Целевое поведение. Сейчас есть только навигационная оболочка /admin, не административные API. Состояние — [STATUS](STATUS.md), порядок реализации — [NEXT](NEXT.md).

## 1. Принцип

Админка — интерфейс управления теми же доменными командами, а не второй backend. Permission проверяется на сервере для каждого чтения и действия. Скрытая кнопка не является защитой. Подробная техническая диагностика не публикуется в пользовательском API.

На старте достаточно одного владельца с разрешёнными полномочиями. Ниже — предлагаемое разделение permissions для роста, а не требование немедленно реализовать пять разных рабочих мест. Пользовательский тариф не даёт административных прав. Первое назначение владельца выполняется отдельной операторской процедурой, не регистрацией с полем role.

## 2. Матрица полномочий

| Действие | Поддержка | Модератор | Финансы | Оператор моделей | Владелец доступа |
|---|---|---|---|---|---|
| Найти аккаунт, увидеть ограниченные сведения | Да | Только нужные для жалобы | Для финансовой операции | Только технический ID задачи | Да |
| Просмотреть приватные prompts/файлы | По отдельному разрешённому разбору с audit | Только материал жалобы | Нет | Не по умолчанию | Не без причины и audit |
| Начислить компенсацию | Только заявка | Нет | Да, в своём лимите | Нет | Да |
| Блокировать/разблокировать | По отдельному permission | По policy, с причиной | Нет | Нет | Да |
| Менять модели и публикацию каталога | Нет | Нет | Только pricing permission | Да | Да |
| Вводить/ротировать secrets | Нет | Нет | Только свои платёжные secrets | Только выданные провайдеры | Да |

Права выдаются по операциям; роли — их удобные наборы. Для опасных действий нужна свежая аутентификация, подтверждение и audit. Суммы порогов и необходимость второго согласования фиксируются до реальных денег; не подставлять произвольные production-лимиты.

## 3. Структура и функции

| Раздел | Что показывает | Что позволяет сделать | Обязательные границы |
|---|---|---|---|
| Обзор | Активные задачи, возраст очереди, ошибки, доступность, использование, расход | Перейти к проблемной области | Временной интервал и свежесть данных; running process не равен здоровому worker |
| Пользователи | Имя/публичный код, статус, способы входа, активность, баланс | Открыть единую карточку, блокировать, отозвать сессии, создать заявку | Нет отдельных дублирующих CRM; PII только по разрешению |
| Баллы | Проводки, резервы, начисления, история компенсаций | Начислить по заявке, сделать компенсирующую корректировку | Причина, идемпотентность, транзакция, запрет редактирования старой проводки |
| Модели | Модальность, capability, provider, ограничения, цена, видимость | Черновик → проверка → публикация/отключение | Рабочие задачи сохраняют свой снимок конфигурации |
| Провайдеры | Настройки endpoints, masked credentials, лимиты, доступность | Ввести/заменить ключ, выключить провайдера, запустить разрешённую проверку | Не отдавать ключ назад; paid test требует согласия и бюджета |
| Исполнители | Последний heartbeat, разрешённые pools/models, версия, занятость | Отозвать token, запретить новые задачи, перевести в drain | Нет удалённой консоли или выполнения присланного shell |
| Задания | Владелец, тип, попытки, timestamps, состояние, связанные assets/расход | Разобрать, запросить отмену, запустить сверку неоднозначного результата | Повторная платная генерация не маскируется кнопкой «Починить» |
| Медиа | Владение, тип, размер, зависимости, состояние обработки/удаления | Разобрать сбой хранения, quarantine по политике | Не общедоступный файловый менеджер; никаких абсолютных путей пользователю |
| Лента/модерация | Публикации, жалобы, причины, статусы | Одобрить, отклонить, снять, рассмотреть обращение | Решение + причина + автор + дата; не удалять оригинал без отдельного основания |
| Боты/почта | Конфигурация доставки, outbox, ошибки | Управлять разрешёнными каналами, тестировать с подтверждением | Polling и webhook имеют одного владельца; не менять webhook при обычном старте |
| Платежи/тарифы | Заказы, события провайдера, сверка, refunds | Только после отдельного платёжного этапа | Успешная страница redirect не доказательство оплаты |
| Аудит/система | Кто, когда и что менял; версии, состояние зависимостей | Фильтровать, экспортировать разрешённые сведения | Нет паролей, полных tokens, signed URLs и сырых provider responses |

Все таблицы: пагинация/фильтры, пустое состояние, ошибка загрузки, время последнего обновления. Данные не грузятся тысячами строк в браузер. На телефоне карточки/детали сохраняют смысл; критическое действие не скрывается за hover.

## 4. Единая карточка пользователя

Вкладки: обзор, способы входа/сессии, задачи, работы (ограниченный доступ), баллы, обращения, административная история. Счётчики имеют одинаковый интервал/определения. Публичное имя не заменяет неизменяемый internal ID.

Сессии показывают платформу, браузер/ОС и допустимые диагностические атрибуты; IP и источник перехода не являются надёжным доказательством личности. MAC-адрес не требуется. Устройство — серверно связанный installation/session identifier, а не выдуманный физический идентификатор.

Отзыв сессии проверяется следующим запросом. Блокировка запрещает новые jobs; судьба уже оплаченной работы и доступ к архиву определяются отдельной явно показанной политикой. Администратор не узнаёт пароль, а восстановление выдаёт пользователю безопасный одноразовый путь.

## 5. Компенсация при перезапуске: обязательный первый сценарий

1. Пользователь создаёт новый аккаунт и обращается за компенсацией.
2. Сотрудник открывает карточку, видит уникальный номер заявки и подтверждённые сведения. Старую БД не импортируют.
3. Уполномоченный сотрудник вводит число баллов, причину и основание. UI показывает получателя и итог до подтверждения.
4. Сервер повторно проверяет permission/лимит и выполняет одну транзакцию: claim уникальной операции, проводка, изменение проекции счёта, audit/outbox.
5. Повтор той же операции с теми же данными возвращает существующий результат. Тот же ключ с другой суммой отвергается.
6. Пользователь видит начисление и причину. Ошибка доставки уведомления не повторяет начисление.

Операционный idempotency key защищает повтор запроса. Отдельный уникальный ключ обработки заявки защищает случай создания новой операции по той же компенсации. Несогласованную повторную компенсацию должен остановить процесс проверки, не только UUID кнопки.

Приёмка: два параллельных подтверждения дают одну проводку; без права — отказ без записи баланса; ошибочная сумма исправляется новой корректирующей проводкой с ссылкой на исходную, не удалением истории.

## 6. Публикация модели

Модель заводится выключенной. Указываются provider/model ID, допустимые inputs/outputs, лимиты, runtime class, timeout, pricing policy и видимость пользователям. Конфигурация версионируется. Автообнаружение каталога провайдера создаёт кандидатов, а не немедленно доступные платные модели.

Проверка конфигурации и fake contract test бесплатны. Реальный probe, если он расходует деньги, отображает лимит и требует подтверждения. Модель публикуется только после успешного поддерживаемого сценария. Доступность и публикация — разные флаги.

Отключение убирает новые submissions; текущая задача использует снимок версии и заданную политику завершения. Повтор/сверка не должны неожиданно уйти к другому провайдеру.

## 7. Разбор зависшей задачи

Оператор видит job ID, attempt ID, provider reference, последнюю фазу, lease и sanitized error. Он различает: задача не отправлена, провайдер принял её, результат неизвестен, файл получен, финализация не завершена.

Доступны безопасные команды: сверить статус, повторить загрузку существующего результата, запросить отмену, закрыть по policy с audit. Команда «повторить генерацию» создаёт явно новую операцию и не выполняется без проверки расходов. Ручная смена статуса в таблице в обход credits/media запрещена.

## 8. Аудит и приёмка

У события: actor, permission/role snapshot, command, target, reason, safe before/after, operation/request ID, время. Секреты заменяются фактом изменения, не значением. При отказе в sensitive action также пишется событие без раскрытия чужих данных.

Минимальная admin-приёмка: пользователь не может читать admin API; сотрудник с ограниченным scope не получает остальные права; начисление идемпотентно; публикация модели не отдаёт ключ в UI; moderation не публикует private original; отзыв worker token закрывает получение новых jobs; все мутации отражаются в audit. Это будущие тесты соответствующих этапов, не уже выполненные проверки Foundation.

Изменения тарифов, оплаты, юридических условий, retention и production-доступа не должны появляться как побочный результат задачи оформления админки.
